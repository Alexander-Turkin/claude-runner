# crun

Автономный раннер задач для Claude Code. Вы описываете задачи в свободной форме,
запускаете одну команду и получаете их выполненными — без подтверждений, с чистым
контекстом на каждой задаче и с git-коммитом после каждой проверенной. Независимые
задачи выполняются параллельно, каждая в своём git worktree.

```
crun
```

Дальше — четыре экрана: выбор проекта, выбор папки с задачами, предпросмотр, подтверждение.
После подтверждения вопросов больше не будет.

Со второго раза выбор не повторяют: раннер помнит прошлый запуск и предлагает его первым
делом, достаточно нажать Enter.

```
Повторить прошлый запуск?  cardholder · tasks/ · opus · без коммитов
[Enter — да, n — выбрать заново]
```

`crun --last` (или `-l`) повторяет прошлый запуск вообще без вопросов, включая
подтверждение, — удобно для повторного прогона после того, как вы доустановили
зависимости из `crun setup`.

Запоминаются: проект, папка задач, модель (если задана флагом `--model` / `--plan-model`) и флаги прогона (`--no-commit`,
`--continue-on-error`, `--allow-dirty`, `--limit`). Флаг, заданный явно в командной
строке, всегда перебивает запомненный. Папка задач и флаги хранятся внутри проекта,
поэтому у разных проектов свои настройки.

## Установка

```bash
bash ~/claude-runner/install.sh
```

Ставит `claude` CLI (если его нет), кладёт симлинк в `~/.local/bin/crun`, дописывает PATH.
Запускать **из обычного терминала**, не изнутри сессии Claude Code.

## Задачи

Одна задача — один `.md`-файл (или папка, см. ниже) в любой папке проекта. Формат произвольный: раннер сам
переведёт текст в свой спек (цель, критерии приёмки, команда проверки, риск, открытые
вопросы) и положит результат в `.claude-runner/compiled/`. **Ваши файлы не изменяются.**

Порядок — по номеру в имени файла: `010-*.md`, либо схема этапов `T0.1`, `T0.2`, `T1.1`.

### Задача-папка: текст, макеты, скриншоты

Если к задаче есть что приложить, сделайте вместо файла **папку** и сложите в неё всё,
что к задаче относится. Ничего размечать не нужно:

```
tasks/
├── T1.2-cards/              ← задача
│   ├── что-сделать.md
│   ├── макет.png
│   ├── пустое-состояние.png
│   └── пример-ответа.json
└── T1.3-login.md            ← обычная задача-файл
```

- **Текст** — все `.md` и `.txt` в папке; компилятор читает их подряд.
- **Материалы** — всё остальное: картинки (PNG, JPG, GIF, WebP), PDF, примеры данных.
  Компилятор их просматривает, и то, что видно на макетах, попадает в критерии приёмки.
  Исполнитель получает тот же список и читает материалы до начала работы.
- Номер и порядок берутся из имени папки, как у файла.
- Подпапкой-задачей считается каталог первого уровня, в котором есть хотя бы один `.md`
  или `.txt`. Каталоги на `_` и скрытые пропускаются: так удобно держать архив (`_done/`).
- Ключ кэша — хэш всех файлов папки: стоит добавить или заменить картинку, и задача
  скомпилируется заново.
- Frontmatter (см. ниже) читается из первого по алфавиту `.md` папки.

`crun new "название"` создаёт такую папку с текстом из шаблона — остаётся положить
в неё картинки.

Компиляция папки с материалами стоит дороже обычной: картинки — это токены.

Если хочется задать всё явно, добавьте frontmatter — тогда компилятор не будет
обращаться к модели:

```markdown
---
title: Экран списка карт
verify: pytest tests/test_cards.py
depends_on: T0.2, T0.3
touches: bot/cards/**, tests/test_cards.py
ticket: PROJ-45
---
Описание задачи…
```

`depends_on` и `touches` управляют параллельностью (см. ниже) и необязательны.

Поле `verify` — команда, которой раннер **сам** проверит результат. Это источник истины:
если модель отчиталась об успехе, а команда упала, задача считается проваленной.

Команда исполняется с каталогами инструментов проекта в `PATH` — `.venv/bin`, `venv/bin`,
`env/bin`, `node_modules/.bin` — поэтому пишется коротко: `pytest -q`, а не
`.venv/bin/python -m pytest -q`. Тот же `PATH` получает и модель, чтобы она проверяла
результат ровно тем же способом. Нестандартное расположение задаётся ключом `toolPaths`
в `.claude-runner.json`.

Проверка всегда идёт под таймаутом (`verifyTimeout`, по умолчанию 300 с): по его
истечении снимается **вся группа процессов**, а не только сам шелл — иначе одна
проверка вешает прогон, а её потомки остаются сиротами.

Команду, которая не завершается по своей природе — `docker compose up` без `-d`,
`npm start`, `uvicorn`, `runserver`, `tail -f` — раннер распознаёт и выполняет как
**проверку живучестью**:

- держит её `livenessTimeout` секунд (по умолчанию 30);
- **продержалась — успех**: сервис поднялся и работает;
- **вышла раньше — провал**, независимо от кода возврата: значит сборка сломалась или
  сервис упал на старте (`docker compose up` возвращает 0 и когда контейнер умер сам);
- затем **прибирает за собой**: снимает группу процессов, а для compose дополнительно
  выполняет `docker compose down --remove-orphans` — контейнеры живут в демоне docker
  и снятием нашего процесса не гасятся.

Срок задаётся на задачу полем `verify_timeout` (в секундах) — во frontmatter или в спеке;
для обычной проверки это потолок ожидания, для проверки живучестью — сколько сервис
обязан продержаться.

Если команды из `verify` нет в `PATH` **до** запуска проверки, раннер её не выполняет:
код 127 под отрицанием (`… && ! cmd …`) превратился бы в 0, и задача была бы засчитана
непроверенной. Вместо этого задача уходит в `blocked`, а в `SETUP.md` появляется пункт
с командой установки — это не провал модели, а нехватка инструмента на машине.
Ненайденные команды видны и в предпросмотре, до старта прогона.

### Попытка исправления

Модель отчиталась `completed`, а проверка раннера упала, — это ещё не провал. Раннер
возвращает модели ошибку **в ту же сессию** (`claude --resume`): она помнит, что и
почему делала, и получает команду проверки, итог и хвост её вывода. Модель чинит,
раннер повторяет ту же проверку, и только второй провал делает задачу проваленной.

```
  проверка: pytest -q
! проверка не прошла (код 1) — попытка исправления 1/1
  • Упал соседний тест на формат даты — поправлю сериализатор
  ✎ Edit   bot/cards/serializer.py
  проверка: pytest -q
✓ T1.2 · 4:31 · $1.12 · 41 шагов · с исправлением
```

- **Срабатывает** на любой провал проверки: код ≠ 0, проверка живучестью не
  продержалась, verify снят по таймауту.
- **Не срабатывает**, если чинить моделью нечего: модель сама вернула `blocked`, команды
  проверки нет на машине (это `crun setup`), упал или вышел по таймауту сам `claude`,
  правки не влились из-за конфликта.
- Те же правила, что и для задачи: никаких `skip`, `xfail`, `noqa` и подгонки тестов.
  Если падает не из-за её работы, модель возвращает `blocked` с причиной.
- Отчёт после исправления — по задаче целиком, поэтому коммит описывает всю работу,
  а не «fix tests».
- `budget` и `timeout` действуют **на каждую попытку**: в худшем случае задача стоит
  вдвое больше бюджета. В итоге прогона стоимость задачи — сумма попыток.
- Число попыток — `fixAttempts` в `.claude-runner.json` (по умолчанию `1`, `0` выключает).
  Сколько их будет, видно в предпросмотре, в строке «Режим».

Не путать с `--retry-failed`: тот возвращает проваленные задачи в очередь на следующем
запуске, и они выполняются заново, в чистом контексте.

## Коммиты

Каждая проверенная задача коммитится одним коммитом вида

```
<type>(<домен>): <что сделано> (<номер в трекере>)
```

например `fix(auth): handle empty password (PROJ-45)`. Коммиты пишутся **на английском**,
даже если задача на русском. Тип, домен, описание и тело коммита (что изменилось и
зачем) даёт исполнитель в отчёте — по тому, что реально сделал. Номер в скобках — поле
`ticket`: из frontmatter, а без него компилятор берёт его из текста задачи, только
если номер трекера там назван явно. Нет номера — скобок нет. Внутренний id задачи
раннера (`T0.1`, `010`) в коммит не попадает. Если исполнитель заголовок не дал,
коммит будет `feat: <title задачи>` — тогда на языке задачи, а тело коммита
возьмётся из его `summary`.

## Разбор задачи с вопросами (`crun plan`)

Если писать задачи руками не хочется, отдайте одну формулировку — раннер разберёт её
на задачи, **предварительно задав вам вопросы**:

```bash
crun plan "добавить теги к заметкам и поиск по тегу"
crun plan brief.md          # формулировка из файла
crun plan --file docs/idea.md
```

Планировщик сначала читает проект (`CLAUDE.md`, `docs/`, структуру), затем задаёт
3–7 вопросов за раунд — до трёх раундов (`planRounds` в `.claude-runner.json`,
бюджет раунда — `planBudget`, по умолчанию $10, таймаут раунда — `planTimeout`,
по умолчанию 900 с). На каждый вопрос три способа ответить:

| Ввод | Что значит |
|---|---|
| текст или номер варианта | ваш ответ |
| Enter | вариант по умолчанию, предложенный планировщиком |
| `-` | **решать вам не нужно** — исполнитель выберет сам и объяснит выбор |

Дальше `crun` пишет файлы задач в папку задач: frontmatter с `title`/`verify`, цель,
критерии приёмки, контекст, раздел «Не входит в задачу» и **«Решения владельца»** —
ваши ответы, перенесённые в постановку. Рядом кладётся готовый спек, поэтому
повторная компиляция этих задач ничего не стоит.

Это единственный момент, когда модель может вас о чём-то спросить: дальше задачи
выполняются автономно, и любая неясность закрывается догадкой исполнителя.

После разбора раннер предлагает сразу запустить задачи:

```
Что дальше?

  1) Запустить задачи
  2) Позже — запуск командой crun

Действие [1-2]:
```

`1` — обычный прогон по этой же папке: предпросмотр и выполнение, без второго
подтверждения. Enter или `2` — ничего не запускается, задачи ждут команды `crun`.
`crun plan "…" --yes` запускает задачи сразу, без меню.

Перед запуском созданные файлы задач коммитятся **отдельным коммитом**
`chore(tasks): add N tasks from crun plan` — только они, ваши staged-правки не
затрагиваются. Иначе прогон остановился бы на грязном дереве, а файлы задач уехали бы
в коммит первой задачи. Если папка задач в `.gitignore`, коммита нет; при `--no-commit`
тоже — тогда новые файлы оставляют дерево грязным, и нужен `--allow-dirty`.

Если планировщик не ответил, раннер называет причину — таймаут, кончился бюджет
раунда, ошибка claude — и ключ, который стоит поднять. Ответ claude и его stderr
по каждому раунду лежат в `.claude-runner/logs/plan-r<N>.json` и `plan-r<N>.err`,
а уже данные вами ответы сохраняются в `.claude-runner/plan-answers.jsonl`, чтобы
диалог не пропал.

## Ответы по готовым задачам (`crun clarify`)

Задачи, написанные руками, компилятор превращает в спек и честно складывает всё
непонятое в `open_questions` — в предпросмотре это строки `⚠ неясно:`. По умолчанию
исполнитель решает их сам. `crun clarify` даёт ответить на них заранее:

```bash
crun clarify              # все невыполненные задачи
crun clarify --only T5.1  # одна задача
```

Ответы уходят в спек задачи (`answers`) и подмешиваются в промпт при запуске отдельным
разделом «Решения владельца» — весомее, чем оставшиеся неясные места. Сводка для
чтения глазами — в `.claude-runner/ANSWERS.md`. Файлы задач при этом не переписываются:
это ваша постановка, раннер её не трогает.

## Что раннеру разрешено

Режим `dontAsk`: разрешено ровно то, что в `config/allow.json`, всё остальное молча
отклоняется. Внутри — чтение и правка файлов проекта, локальные утилиты, git на чтение,
сборка и тесты, **Docker**, а также **сеть на чтение и MCP**.

**Сеть.** `WebFetch` и `WebSearch` доступны без настройки — чтобы модель сверялась с
актуальной документацией библиотек, а не полагалась на устаревшие знания. `curl`, `wget`
и установка пакетов по-прежнему запрещены: читать можно, менять систему нельзя.

**MCP.** Подключённые у вас MCP-серверы доступны автоматически. Раннер сам находит их
в `~/.claude.json` и `.mcp.json` проекта и выдаёт права на их инструменты: allow-правила
не принимают голый `mcp__*`, шаблон разрешён только после literal-префикса, поэтому
серверы перечисляются поимённо как `mcp__<сервер>__*`. Серверов нет — ничего не сломается,
в предпросмотре будет написано, что их не настроено.

**Docker.** `docker` и `docker compose` разрешены целиком: поднять стек, прогнать
миграции внутри контейнера, посмотреть логи, погасить всё через `down -v`. Запрещены
только глобальные чистки (`docker system|volume|image|network|container|builder|buildx
prune`) — они сносят образы и тома чужих проектов на машине, а не проекта задачи.

**Пакеты.** Установка разрешена: `pip`, `npm`, `brew`, `uv`, `poetry`, `cargo`, `go`,
включая интерпретаторы из `.venv`. Запрещены глобальные установки (`npm i -g`,
`pip install --user`), публикация (`npm publish`, `twine upload`) и удаление системных
пакетов (`brew uninstall`) — ставить в проект можно, менять машину нельзя.

Установленные зависимости защищены от записи: `.venv`, `node_modules`, `site-packages`,
`vendor` доступны только на чтение. Это не теория — на тесте модель отредактировала
`__init__.py` внутри `site-packages`, чтобы прошла проверка на `__version__`. Правка чужой
библиотеки ради зелёной галочки не должна быть возможной.

**Запрещено:** секреты (`.env`, `~/.ssh`, keychain, `env`/`printenv`), `sudo`, `rm`,
`curl`/`wget`, изменяющие команды git (`push`, `remote add`).

Секреты закрывает не список правил, а PreToolUse-хук `hooks/guard-secrets.sh`: он
разбирает фактическую команду и ловит обход в любой форме — `cat ./.env`, `bash -c "…"`,
`grep` по абсолютному пути. Шаблоны (`.env.example`, `.env.sample`, `.env.template`,
`.env.dist`) секретами не считаются: они коммитятся в репозиторий, и запрет на них —
ложное срабатывание, которое стоило целой задачи. В составной команде это работает
пофайлово: `cat .env.example && cat .env` по-прежнему блокируется. Он же проверяет URL сетевых запросов: ключ или токен в
query-строке блокируется, чтобы открытая сеть не стала каналом утечки. Каждое
срабатывание пишется в `.claude-runner/logs/guard.log`.

**Если нужно сузить** — в `.claude-runner.json` проекта:

```json
{
  "network": { "enabled": false },
  "network": { "domains": ["pypi.org", "*.readthedocs.io"], "search": false },
  "install": { "enabled": false },
  "mcp": false,
  "mcpConfig": "mcp.json"
}
```

`install.enabled: false` возвращает прежнее поведение: не хватает зависимости — задача
останавливается и пишет команду установки в `crun setup`.

`domains` ограничивает список доменов, `mcpConfig` подключает ровно один свой конфиг
вместо ваших глобальных серверов.

## Модели

По умолчанию всё делает **Opus**: и компилирует задачи (понять размытую постановку —
самое дорогое место для ошибки), и выполняет их.

Переопределяется флагами `--plan-model` / `--model` или в конфиге проекта. Дешёвый режим —
реализация на Sonnet: `crun --model sonnet` или `"model": "sonnet"` в `.claude-runner.json`.
Opus дороже — если задачи упираются в `budget`, поднимите его там же.

**Effort** (глубина рассуждений, флаг `--effort` у `claude`) тоже разный по этапам:

| Этап | По умолчанию | Ключ в `.claude-runner.json` |
|---|---|---|
| планирование: `crun plan` и компиляция задач | `xhigh` | `planEffort` |
| выполнение задач | `high` | `effort` |

Допустимые значения: `low`, `medium`, `high`, `xhigh`, `max`. Чем выше effort, тем больше
токенов уходит на рассуждения: если компиляция или задачи начинают упираться в бюджет,
поднимите `planBudget` / `compileBudget` / `budget` или снизьте effort.

**Бюджет** — потолок трат на один вызов `claude` (`--max-budget-usd`), а не расход:
модель тратит столько, сколько нужно, а лимит лишь обрывает зациклившийся вызов.

| Этап | По умолчанию | Ключ в `.claude-runner.json` |
|---|---|---|
| раунд `crun plan` | $10 | `planBudget` |
| компиляция одной задачи | $10 | `compileBudget` |
| выполнение одной задачи | $10 | `budget` |

## Параллельность

По умолчанию раннер выполняет **до трёх задач одновременно** (`--jobs N`, ключ `jobs`).
Задача берётся в работу, как только закрыты её зависимости, — очередь не ждёт
завершения соседей.

Каждый поток работает в своём **git worktree** внутри `.claude-runner/worktrees/`, а не
в общем дереве. Это не роскошь: `verify` — источник истины раннера, и в общем дереве
проверка одной задачи спотыкалась бы о недописанный код другой, а `git add -A` одной
задачи забирал бы правки другой в свой коммит. Задача коммитится в ветке своего слота
и вливается в основную ветку по одной; конфликт вливания — это провал конкретной
задачи с внятным сообщением, а не обрыв прогона.

Раннер не запускает задачу одновременно с соседней, если:

- она от неё **зависит** (`depends_on`);
- их **области правки пересекаются** (`touches`);
- её `verify` — **проверка живучестью** (`docker compose up`, dev-сервер): такая задача
  занимает порты и имена контейнеров, поэтому идёт в одиночку.

Пустой `touches` означает «область неизвестна» — задача считается совместимой с любой.
Планировщик (`crun plan`) заполняет оба поля сам и режет постановку так, чтобы
независимых задач было больше.

Разбиение на волны показывается в предпросмотре до запуска:

```
волна 1: T4.1, T4.2 · волна 2: T4.3
```

### Окружение слотов

В worktree попадает только то, что в git. Недостающее раннер подставляет симлинками:
`.venv`, `venv`, `env`, `node_modules`, `.env` — список меняется ключом `worktreeLink`.

В умолчание намеренно **не входят** `data/`, `*.db` и прочее изменяемое состояние:
одна база на несколько параллельных задач — это гонка. Если вашим проверкам состояние
всё-таки нужно, добавьте каталог в `worktreeLink` осознанно.

Для проектов, поставленных как editable (`pip install -e .`), раннер дополнительно
выставляет `PYTHONPATH` на worktree. Без этого `pytest` импортировал бы код основного
дерева — в `.venv` зашит абсолютный путь к исходникам, — и проверка проходила бы,
ничего не проверив.

### Когда параллель выключается сама

Раннер откатывается на один поток и говорит, почему, если изоляцию не построить:
проект не git-репозиторий, задан `--no-commit` или `--only`, дерево грязное при
`--allow-dirty` (worktree режется от HEAD и ваших правок не увидит), или ветка
`crun/wN` содержит невлитые коммиты.

Параллельно компилируются и сами задачи: вызовы модели независимы, и десяток
нескомпилированных задач перестаёт стоить десять минут.

Одно следствие, о котором стоит знать: параллель во столько же раз повышает частоту
обращений к API. Бюджет остаётся пожадачным (`budget`), но упереться в лимиты
провайдера теперь возможно — тогда помогает `--jobs 1`.

## Прогресс и обратная связь

По ходу задачи видно, что делается, зачем и что из этого вышло:

```
[2/7] T0.2 · Конфигурация и логирование
  • Тестов в проекте нет, поэтому проверю импортом
  ⋯ Read   02-architecture.md
  ✎ Write  bot/config.py
  $ python3 -c 'import bot.config'
  ⊘ Blocked by crun secret guard: …
  ⋯ ещё работаю (1:05 · шагов 7)
  ✔ Запустил python3 -c 'import bot.config' — импорт прошёл без ошибок
  изменено: bot/config.py bot/logging.py
✓ готово · 1:12 · $0.38 · 14 шагов
```

`⋯` чтение · `✎` запись · `$` команда · `⊘` отказ · `•` реплика модели ·
`✔` чем подтверждён результат · `изменено` — что реально поменялось на диске.

Список изменённого берётся из git сравнением с состоянием до задачи, а не из
самоотчёта модели, поэтому в него не попадают чужие правки при `--allow-dirty`.

Если шаг долгий, раз в 20 секунд печатается строка «ещё работаю» со счётчиком шагов —
видно, что процесс жив.

**Про рассуждения.** Внутренний reasoning модели показать нельзя: в потоке блоки
`thinking` приходят с пустым текстом, остаётся только подпись. Поэтому `prompts/system.md`
просит модель коротко проговаривать вслух, что она делает и почему, — эти реплики и
видны как `•`. Если хочется меньше слов, правьте раздел «Проговаривай ход работы».

`--quiet` убирает построчный вывод; полный транскрипт всё равно пишется в
`.claude-runner/logs/<id>.jsonl`.

## Прерывание

Ctrl+C останавливает прогон, снимает **все** запущенные `claude` и прибирает временные
файлы. Уже скомпилированные задачи и выполненные шаги сохранены: следующий запуск
продолжит с того же места, а не начнёт заново. Worktree прерванного прогона остаются
и переиспользуются следующим запуском — чистить их руками не нужно.

Провал задачи без `--continue-on-error` останавливает **запуск новых** задач, но уже
идущие доводятся до конца и вливаются: эта работа уже оплачена. Задачи, зависящие от
провалившейся, помечаются пропущенными с указанием причины.

## Настройка на проект

`.claude-runner.json` в корне проекта:

```json
{ "planModel": "opus", "model": "opus", "planEffort": "xhigh", "effort": "high", "budget": 10, "timeout": 1800,
  "fixAttempts": 1, "jobs": 3, "worktreeLink": [".venv", "node_modules", ".env"],
  "extraAllow": ["Bash(pip install*)"], "extraDeny": [] }
```

## Команды

```
crun                       выбрать, показать план, запустить
crun <проект> [папка]      без интерактивного выбора
crun compile               только скомпилировать и показать, как поняты задачи
crun status                что сделано, что осталось
crun setup                 что доустановить и настроить руками
crun new "название"        создать папку задачи из шаблона
```

Флаги: `--yes`, `--last`, `--dry-run`, `--only <id>`, `--limit N`, `--jobs N`, `--model`,
`--plan-model`, `--quiet`, `--no-commit`, `--continue-on-error`, `--retry-failed`,
`--recompile`, `--allow-dirty`.

Коды выхода: `0` — всё сделано, `1` — задача провалена, `2` — нужен ваш ввод.

## Что появляется в проекте

```
.claude-runner/
├── compiled/    спеки задач (.json) и их читаемые версии (.md)
├── state.json   статус каждой задачи
├── PROGRESS.md  история выполненного — подмешивается в контекст следующих задач
├── last.json    выбор прошлого запуска (crun --last)
├── SETUP.md      накопленный список ручных шагов (crun setup)
├── setup.json   он же машинно-читаемо
├── worktrees/   рабочие копии слотов параллельного прогона
├── locks/       взаимное исключение при записи состояния и вливании в git
└── logs/        сырые ответы (<id>.jsonl, попытки исправления — <id>-fix1.jsonl),
                 вывод verify, guard.log, LAST_FAILURE.md
```

Статус хранится в `state.json`, поэтому исходные файлы задач никуда не двигаются.
Ключ задачи — SHA её содержимого: правка исходника автоматически требует перекомпиляции.

## Границы

Allow-лист и хук защищают от случайного вреда, но это не песочница ОС: у Клода есть
доступ на запись к файлам проекта. Настоящая страховка — git-коммит на каждую задачу:
любую можно откатить через `git revert`. Раннер требует чистое рабочее дерево перед
стартом, чтобы чужие изменения не попали в его коммиты.
